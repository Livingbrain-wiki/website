Agent logs

The livingbrain logs commands: what is read, what is redacted, and what is sent when you opt in.

Source: docs/logs.md on GitHub, at commit 7163b59 (2026-10-16).

livingbrain logs sync reads the session logs your local coding agents already wrote — Claude Code under ~/.claude/projects, Codex under ~/.codex/sessions — and uploads the sessions whose repository you have opted in, one normalised source per session — and beside each one a short note, a searchable page filed under the repository's name, so the session turns up in livingbrain search and livingbrain ask. Nothing is read that you did not already have on disk; nothing is sent that you did not allow.

Use it

cd ~/work/demo
livingbrain logs allow          # opt this repository in (detail: full)
livingbrain logs allow --detail messages  # …or send messages only, no tool I/O
livingbrain logs sync           # read local logs, upload this repo's sessions
livingbrain logs sync --dry-run # report what would go, send nothing
livingbrain logs status
livingbrain logs deny
commandwhat it does
logs allow [path] [--detail full|messages|summary]allow sessions whose log records a working directory inside path (default: the current directory), at a detail level (default full for a new path; an allowed path keeps its level unless --detail names one)
logs deny [path]revoke a path logs allow added
logs statusprint what is opted in, at which detail level, and where that is recorded
logs syncread both agents' logs and upload the opted-in sessions
logs show <file>print the redacted record logs sync would send for one session file, opted in or not; never touches the network. --json gives {file, opted_in, redacted, body, record}: body is the exact text, record its parse (null if redaction left it unparseable)
flagwhat it does
--claude-dir <dir>read Claude Code sessions from here instead of ~/.claude/projects
--codex-dir <dir>read Codex sessions from here instead of ~/.codex/sessions
--dry-runparse, normalise and report, but never touch the network
--session <file>logs sync only: scan just this session file (repeatable). It must sit under one of the two trees, and its repo must still be opted in

--json prints one object: scanned, uploaded, unchanged, skipped, unreadable (a file that could not be read at all), unparsed (read, but no session in it), redacted, dry_run and a sessions array of {agent, session_id, repo, models, turns, tool_calls, totals, truncated, detail, status, branch, started_at, ended_at, file, note?} (file is the local path of the log; it is printed, never sent) — the status one of uploaded, unchanged, skipped (reason: "repo not opted in") or would_upload under --dry-run. Every opted-in session also carries note: {slug, project, status, id?, url?, error?}, the status one of written, unchanged, failed or would_write under --dry-run (null for a session that recorded no repository), and the top level counts them in notes, e.g. {"written": 2}.

Find a session again

A source in the ledger is not yet a page, and search and ask read pages. So once a session's source is in the ledger — uploaded, or already there — logs sync also writes it a note through POST /v1/notes, in your personal scope, filed under the project named after the repository's directory (~/work/demo files under demo). Filter on it:

livingbrain search --project demo "migration"
livingbrain ask --project demo "what did we decide about the migration?"

The project filter runs before the result limit, so --project answers with up to --limit of that project's pages however many other pages match too.

The note is the session, readable: a header (agent, session id, repository, branch, first and last timestamp, models, message and tool-call counts, token and cost totals, detail level, the id of the source and a link to its full transcript), then the conversation in order — every user and assistant message, reasoning summaries quoted, events (an interruption, a compaction) as a line, and each tool call as a compact block: its name, file and outcome (ok/error, exit code), its command or patch in a fenced block, and its result in another, clipped to head and tail.

A page must fit the notes route's 64 KiB request limit, so the note is held to 48 KiB (measured as the JSON-escaped text it travels as). A long session is first quoted less — each message, input and result clipped harder, down to commands without results — and if it still does not fit, the page keeps the opening turns and the most recent ones, with a line saying how many sit between and linking the full transcript. It is built from the same home-elided, redacted record as the source and redacted again on this machine before it is sent; the notes route redacts again on arrival.

Read the whole transcript

The web app's Agent sessions view (wiki.html?view=sessions) lists your sessions, one row per session (a re-sync after an upgrade files a new source beside the old one; the newest is the one listed). Each opens its transcript at wiki.html?view=sessions&source=<id>, read from GET /v1/sources/{id} — which returns the body to its owner under the same rules as the listing, by bearer token or by the web app's session cookie — and drawn turn by turn: messages in full (the agent's as markdown, the person's as typed), reasoning summaries folded, tool calls with their commands, patches and results, long results folded. Nothing is drawn with innerHTML: every node is built element by element, so nothing in a transcript can become markup.

A subagent is a card inside the call that launched it — 🤖 name · model · duration · tokens · status, its task, its final answer — indented on a rule, with its other turns drawn only when Show steps is pressed (a subagent can run hundreds). The session's header names its main model and its subagents, and a turn names its model where it changed.

The Mac app's Recent Sessions view shows the same record, built locally by livingbrain logs show <file>, subagents nested the same way.

Notes are idempotent too. Each is keyed by agent and session — agent-log-<agent>-<session-id> — so a session that grew updates its one page in place, and a re-sync of an unchanged session sends the same note, which the server recognises and does not write (status: "unchanged"). A note the server refuses — say, because someone edited that page by hand — is reported as failed with the reason; the session's source is in the ledger regardless, and the next sync tries the note again.

A note is a session page (entity type session), not a wiki page: it is a source the coding-agents wiki is compiled from, so the web app lists it under Sources → Agent sessions and keeps it out of Pages (search and ask still find and cite it). Its title names the session the way a person would: EarthOS.world · Claude Code · 2026-10-15 · Fix the login redirect loop — the project, the agent, the day it started and the first thing asked, cut to 60 characters. A client that sends only an id-shaped title (colonizer session a15f…) gets one the server reads from the note itself; for a Colonizer colony that is the issue it worked on, else its pull request, else its outcome (EarthOS.world · Colony a15fba01 · #123 Fix auth redirect). Notes synced before this were decisions titled by id: the notes module's cron moves them to session and renames them, a batch every 5 minutes, and a session's next sync does the same for its own page.

Opt-in is per repository

The opt-in is a small JSON file in the CLI's config directory ($XDG_CONFIG_HOME/livingbrain/logs-allow.json, else ~/.config/livingbrain/logs-allow.json), listing absolute paths. A session counts as opted in when the working directory its log records sits inside an allowed path — so allowing a repository's root covers its subdirectories, which is what a monorepo needs and what running logs allow at the root means.

Each allowed path also has a detail level, kept beside it in the same file ("detail": {"/abs/path": "messages"}); a path with no level — every entry written before levels existed — is full:

levelwhat a session's record carries
fullevery user and assistant message in full, reasoning summaries, events, and each tool call with its input and its clipped result
messagesevery message in full and each tool call's name — no tool input or output, no reasoning
summaryeach message cut to 2 000 characters and tool names only — what every record carried before levels existed

When a session's directories fall under several allowed paths, each directory takes the level of the most specific path it sits in, and the session is sent at the most restrictive of those. A level this build does not know makes the file unreadable rather than guessed at; a build that predates levels ignores them and sends summary. A path that does not exist on this machine is allowed all the same: a checkout need not be mounted here to be opted in. A symlinked checkout matches too: a directory counts when either its recorded form or the path it really is sits inside an allowed root.

A session may run in more than one directory, and the decision covers all of them: a session whose log shows a working directory outside every allowed path is skipped, however opted-in its first repo was. Fail closed, on purpose — half a session is still a leak.

A corrupt opt-in file, or one written by a newer version of the CLI, is an error rather than an empty allowlist: silently reading it as empty would sync exactly the sessions you meant to keep off the wire.

What a session becomes

Both formats normalise into one record, versioned with schema_version (3) and a per-collector collector_version (3): the agent, the detail level it was built at, session id, repository, branch, models, first and last timestamp, the turns, totals (tokens in/out, cache read/write, reasoning, cost when the log reports one — the main agent's own; each subagent carries its own), truncated, omitted_turns and omitted_subagent_turns.

The turns are the conversation in order. Each has a role, a timestamp, its text and its tool_calls:

  • user — what the person typed, with the agents' own machinery taken out: Claude Code's <system-reminder> blocks, slash-command wrappers (a /review src/lib.rs stays, <local-command-stdout> goes), ! shell output, task notifications and meta lines; Codex's developer messages, <permissions instructions>, <environment_context>, <user_instructions>, AGENTS.md dumps and the like. A user line that was only machinery is no turn.
  • assistant — the agent's text, the model that wrote it (named only where it differs from the list's previous assistant turn, so a session on one model names it once), and the tool calls of that step, each {name, format?, path?, input?, output?, status?, exit_code?, subagent?}: input is the command (exec_command's cmd, Bash's command), the patch (apply_patch), the diff of an Edit under its path, or the arguments as compact JSON; format (shell, diff, json, text) says how to show it. output is the result — clipped to its first and last 2 KiB around a … N bytes omitted … line — with status (ok, error, interrupted) and exit_code when the log records them. An input is clipped the same way at 16 KiB.
  • reasoning — a reasoning summary, when the log carries one in the clear (Codex's summary, Claude Code's visible thinking). Encrypted reasoning is never read.
  • event — something that happened rather than something said: an interruption (Codex's <turn_aborted>, Claude Code's [Request interrupted by user]), a context compaction, or the turns the size cap removed.

A message is kept whole up to 256 KiB (beyond that, its first and last 128 KiB); what bounds a session is the body cap below. Under messages and summary, the tool-call objects carry name alone.

A version-1 record (from a build before this one) reads the same way: its tool calls are names, it has no reasoning or event turns, and its text was cut to 2 000 characters. A version-2 record has no subagent, no turn model and no omitted_subagent_turns; it reads the same way too.

Subagents

A tool call that launched a subagent carries the subagent's whole session in subagent, every field always present, in this order:

{"name": "Agent", "format": "text", "input": "Find every logger in src/",
 "output": "Two loggers: src/a.rs and src/b.rs.", "status": "ok",
 "subagent": {
   "id": "a1111", "name": "Explore", "description": "Survey logging",
   "models": ["claude-haiku-4-5"],
   "started_at": "2026-10-02T10:00:06.500Z", "ended_at": "2026-10-02T10:01:30.000Z",
   "status": "completed",
   "totals": {"input_tokens": 180, "output_tokens": 45, "cache_read_tokens": 0,
              "cache_creation_tokens": 0, "reasoning_tokens": 0, "cost_usd": null},
   "turns": [ …the same turn shape, recursively: its own tool calls and subagents… ],
   "truncated": false, "omitted_turns": 0}}

name is the kind of agent (Claude Code's subagent_type, Codex's agent role, Colonizer's subagent), description what the launch said it was for, status one of completed, failed, stopped, running (or null when the log does not say). The call's output is the subagent's last words, as a foreground call's result already is — a background launch's receipt is replaced by them. The detail level, home elision, redaction and the clips all apply inside a subagent exactly as outside it.

  • Claude Code writes each subagent's transcript beside the session: ~/.claude/projects/<dir>/<session>/subagents/agent-<id>.jsonl, and its launch in agent-<id>.meta.json (agentType, description, the launching toolUseId, parentAgentId for one a subagent launched). The transcript nests in the call with that id — the session's own, or the parent subagent's — and the status is the last <task-notification> for that call (else the call's result). The subagent's working directories count for the opt-in like the session's own.
  • Codex writes a spawned agent's rollout as a file of its own, whose session_meta names source.subagent.thread_spawn (parent_thread_id, agent_path, agent_role, agent_nickname). It nests in the spawn_agent call whose result names that path, and is no longer synced as a session of its own. Codex's own helpers (source.subagent.other) are still sessions of their own.

Two formats, two rules worth knowing:

  • Claude Code streams one assistant message as several JSONL lines that repeat the same message.id, the same usage and the same costUSD. All three are counted once per id — five blocks are one request. A tool's result arrives on a later user line and is paired with its call by id.
  • Codex writes token_count events whose total_token_usage is cumulative, so the last one is the session's totals; summing them would multiply every turn in. A call's output is paired with it by call_id.

Redaction happens on both sides

Redaction is local and not optional. Before anything serialises, the real home prefix becomes ~ — in the recorded repository path and in every string a turn carries (text, tool paths, inputs, outputs) — including Claude Code's dash-encoded project-dir form of directories under $HOME (-home-alice-…). Every one of those strings then goes through livingbrain-redact, the same library the server runs on every ingest path, value by value, before the record is serialised: redacting the serialised JSON instead can let a match straddle an escape (an address after a \n read as nname@host) and leave bytes that no longer parse. The serialised body is checked once more as a whole, the way the server will read it, and the redacted bytes are what the socket sends. A secret in a tool's output is redacted like one in a message.

Size limits

whatlimit
one tool result in the recordfirst and last 2 KiB
one tool input in the recordfirst and last 8 KiB (16 KiB)
one message in the record256 KiB (first and last 128 KiB beyond)
the record's body768 KiB (three quarters of redaction's 1 MiB input cap, which the server applies to the whole body on arrival) and 992 KiB once JSON-escaped (what GET /v1/sources/{id} answers it inside, under the edge's 1 MiB response buffer)
the note48 KiB JSON-escaped (the notes route takes 64 KiB)

A session past the body cap loses its subagents' detail first: subagent by subagent, oldest first, each loses its inner turns from the oldest on — never its header or its final answer — until the body fits; the removed run becomes one event turn in the subagent, which says so in its own truncated and omitted_turns, and the record counts them in omitted_subagent_turns. Still past the cap, the session keeps its opening turn and its most recent ones: the oldest turns after the opening are removed whole, an event turn says how many, truncated is true and omitted_turns counts them. One session is one source either way, so the ledger's (scope, sha256) key still holds.

Idempotency

Sessions land as kind: "agent_log" in the source ledger, filed as <agent> session <id>, in your personal memory — there is no --shared for logs. The ledger's key is (scope, sha256 of the redacted body), and a record serialises deterministically: struct order is wire order, and nothing in it is read from the clock or the environment. The same session therefore always yields the same bytes, and re-running logs sync reads rows back (200, unchanged) instead of storing copies.

A session whose record changed — it grew, its repository's detail level changed, or a CLI upgrade changed the schema — yields different bytes, so the next sync uploads it as a new source (201) and rewrites its note in place (same slug, a new version). There is no local cache that could skip it: the ledger's own key is the only dedupe.

Projects, and listing what was synced

Each upload also names a project: the basename of the session's repository (~/code/livingbrain files as livingbrain), cut to the server's project rule — ASCII letters, digits, ., _ and -, starting with a letter or digit, at most 64 bytes; any other character becomes -. A session that recorded no repository names none. Only the basename travels in this field; the full home-elided path is already inside the record. The server redacts the project like any other free text and drops it, rather than storing it, if redaction finds anything in it.

The project is a column of the ledger row, not part of the body, so it does not change the (scope, sha256) key: a session synced before projects existed is filed under its project the next time logs sync runs (200, unchanged — the existing row gains the project; a row that already has one keeps it).

List what is there, newest first, without opening a single body:

livingbrain sources --kind agent_log                 # every synced session
livingbrain sources --kind agent_log --project demo  # one repository's
livingbrain sources --projects                       # the projects, with counts
livingbrain sources --cursor <next_cursor>           # the next page

The same lists back the web app's Agent sessions view (wiki.html?view=sessions) and the project filter beside the wiki's search box. The listing is strictly yours: your personal sources, plus the workspace's shared ones — never another member's, never another workspace's.

GET /v1/sources

?kind=&project=&agent=&limit=&cursor=, bearer-authenticated exactly like GET /v1/sources/{id}. agent narrows to the sessions one agent wrote (claude_code, codex, colonizer: the first word of the session's path). limit defaults to 50 and is clamped to 100; a kind or project outside its rule is a 400 validation-failed, not an empty list. Rows are newest first (ULID order); next_cursor is the last id of a full page, null on the last one.

{
  "sources": [
    {
      "id": "01JA7Q8ZK3T5V9X2B4N6M8P0RC",
      "kind": "agent_log",
      "scope": "personal",
      "path": "claude-code session 3f2a9c1e-5b7d-4e8a-9c1f-2a4b6d8e0f1a",
      "project": "livingbrain",
      "held": false,
      "created_at": "2026-10-15T04:32:12.801Z"
    }
  ],
  "next_cursor": null
}

GET /v1/sources/projects

?kind= optional. The distinct projects your sources are filed under, alphabetically, with a count each — the names GET /v1/sources?project= can find something under, and no others (at most 500).

{ "projects": [ { "project": "demo", "sources": 2 }, { "project": "livingbrain", "sources": 14 } ] }
